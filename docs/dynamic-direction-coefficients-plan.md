# План: коэффициенты направления в динамическом взвешивании

Статус: рабочий документ. Этапы выполняются последовательно и отмечаются после проверки.

## Цель

Привести динамическое взвешивание к ТЗ: статическая калибровка задаёт базовый вес по коду АЦП, а отдельный поправочный коэффициент учитывает направление движения.

```text
статический вес = код АЦП * калибровочное число статической точки / 65535
динамический вес = статический вес * поправочный коэффициент направления
```

## Согласованные решения

- На форме: `Поправочный коэффициент направления ->` и `Поправочный коэффициент направления <-`.
- В коде:

  ```csharp
  RightDirectionCorrectionFactor
  LeftDirectionCorrectionFactor
  ```

- Направление выделяется в отдельный тип:

  ```csharp
  enum Direction
  {
      Right,
      Left
  }
  ```

- В PostgreSQL используется таблица `direction_correction_profiles` с полями `right_direction_correction_factor` и `left_direction_correction_factor`. Таблица `calibration_dynamic` удаляется без переноса данных.
- В `settings.json` кэш профиля также использует `RightDirectionCorrectionFactor` и `LeftDirectionCorrectionFactor`; значения старого формата не сохраняются.
- Старые динамические коэффициенты имеют смысл `тонны / код АЦП`, а новые будут безразмерными поправками. В отладочной базе старые профили очищаются, автоматическое преобразование не выполняется.
- Исторические результаты не связываются с калибровкой задним числом: достоверно определить применённую точку уже нельзя.
- Изменение статической калибровки не деактивирует профиль коэффициентов направления автоматически. Повторная настройка коэффициентов направления выполняется только по решению оператора.

## Текущее состояние

Сейчас динамика рассчитывает вес напрямую:

```text
динамический вес = код АЦП * K направления
```

На сервисной форме `K` рассчитывается как `эталонная масса / код АЦП`. Статические точки в динамическом расчёте не используются. Это расходится с ТЗ, где коэффициент направления задан как поправка к весу.

## Целевая цепочка данных

```text
код АЦП выбранного канала
  -> выбор активной статической точки
  -> статический вес
  -> поправочный коэффициент направления
  -> динамический вес
  -> сохранённый результат и аудит
```

Для каждой динамически взвешенной тележки сохраняются идентификатор статической точки и статический вес. Для вагона также сохраняются идентификатор профиля направлений и выбранное направление.

### 4. Основная форма динамического взвешивания

**Файл:** `Forms/DynamicWeighingForm.cs`.

- [ ] Получать базовый вес по статической точке текущего канала.
- [ ] Умножать базовый вес на коэффициент выбранного направления.
- [ ] Затем применять существующие правила нуля и дискретности.
- [ ] Перед взвешиванием проверять наличие активной статической точки, активного профиля направлений и положительного коэффициента выбранного направления.
- [ ] При отсутствии любого условия блокировать взвешивание понятным сообщением.

Целевой фрагмент:

```csharp
var staticResult = CalculateStatic(_ldb.CalibPoints, adcCode, _sim.Channel);
double factor = direction == Direction.Right
    ? _ldb.ActiveDirectionCorrectionProfile.RightDirectionCorrectionFactor
    : _ldb.ActiveDirectionCorrectionProfile.LeftDirectionCorrectionFactor;
double dynamicTonnes = staticResult.Tonnes * factor;
```

## Сценарии проверки

- [ ] Статическая точка даёт базовый вес 100 т; коэффициент `-> = 1.000000` даёт динамический вес 100 т.
- [ ] При `-> = 1.020000` тот же базовый вес даёт 102 т.
- [ ] Коэффициент `<-` применяется только для направления влево.
- [ ] Авторасчёт для эталона 100 т и статического веса 100 т даёт `1.000000`.
- [ ] Без активной статической точки динамический расчёт и калибровка блокируются.
- [ ] Без нового профиля коэффициентов динамическое взвешивание блокируется.
- [ ] После деактивации статической точки старый результат сохраняет ссылку на неё, а новый расчёт её не выбирает.
- [ ] В `wagon_weighing` и аудите для нового динамического результата есть две ссылки на статические точки и ссылка на профиль направления.
- [ ] Плановая очистка удаляет результат и аудит старше срока без ошибки внешнего ключа; статические точки и профили остаются в истории.

## Неавтоматизируемые решения

- Интерполяция статических точек не вводится этой доработкой.
- Старые динамические коэффициенты не преобразуются.
- Для исторических результатов не подбирается калибровка задним числом.
- Расширение формы корректировок для отображения связей требует отдельного решения по интерфейсу.
